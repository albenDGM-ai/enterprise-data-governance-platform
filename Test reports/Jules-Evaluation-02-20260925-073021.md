## 1. Objective
This evaluation tests engineering judgment, traceability, and safe implementation by requesting the identification and resolution of a genuine behavioral or contract gap within the existing lineage functionality of the DGM backend.

## 3. Investigation
- Inspected models: `DataLineageFlow`, `DataLineageTransformation`, `DataLineageTarget`, `DataLineageMapping`.
- Inspected services: `LineageMappingService`, `LineageTargetService`, `LineageTransformationService`, `LineageFlowService`.
- Inspected routers/API: `/backend/app/api/routers/lineage.py`.
- Inspected tests: `test_batch_08_graph_integrity.py`.
- Trace: A Flow owns Transformations. A Transformation owns Targets. Mappings connect to Targets and Transformation. The API contract passes updates down to the services.
- Mapping relationships enforce that transformations and targets must belong to the correct flow during creation and updates.

## 4. Baseline Behavior
- Before the change, `LineageTargetService.update` did not verify if an updated `lineage_transformation_id` belonged to the same `LineageFlow` as the Target's original transformation.
- A cross-flow replacement was possible, corrupting the graph integrity and implicitly moving the target across flows.
- Running the custom baseline verification script demonstrated that no `LineageRelationshipValidationError` was raised when changing a target's transformation to one in a different flow.

## 5. Identified Gap
- **Gap:** The Target update path does not enforce the same invariant as Mapping. While `LineageMappingService.update` ensures we don't cross flows, `LineageTargetService.update` blindly accepts any active `lineage_transformation_id`, even if it belongs to a different `LineageFlow` than the Target's original transformation.
- **Why it is a real issue:** Because Mappings enforce flow-consistency based on Target Flow paths, allowing a Target to arbitrarily switch Flows invalidates downstream lineage graph expectations and breaks established ownership boundaries.
- **Where:** `backend/app/services/lineage_target_service.py` -> `update` method.
- **Scope:** It is a small behavioral inconsistency fixable without architectural or database schema changes.

## 6. Implementation
- Changed: `backend/app/services/lineage_target_service.py`.
- Why: Added validation in `LineageTargetService.update` that checks if the `old_transformation` and `new_transformation` have different `lineage_flow_id`s, raising a `LineageRelationshipValidationError` if they do. This correctly bounds the update.

## 7. Regression Test
- Added test: `test_target_update_rejects_a_cross_flow_replacement` in `backend/tests/test_batch_08_graph_integrity.py`.
- The test demonstrates that calling `service.update` to replace a target's transformation with one belonging to a different flow correctly raises `LineageRelationshipValidationError`.
